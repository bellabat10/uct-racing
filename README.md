# UCT Racing – Suspension Hardpoint Optimisation

Kinematic optimisation of suspension hardpoints, built on the `kinematics`
solver package.

## Repo layout

- `configs/solidworks_points.yaml` — raw hardpoints exported from SolidWorks
- `configs/convert_coordinates.py` — converts SolidWorks points to ISO 8855
- `configs/uct_front_geometry_generated.yaml`, `uct_rear_geometry_generated.yaml`
  — converter output; these are what the scripts actually read
- `suspension-model/` — git submodule, the `kinematics` solver (installed
  editable via `pip install -e .`)
- `scripts/mount_kpi_sweep.py` — Stage A: merged mount-height (Z) x KPI grid
  sweep (see below)
- `scripts/caster_trail_analysis.py` — Stage B: caster / mechanical-trail
  refinement on top of Stage A's winning geometry
- `scripts/build_optimal_geometry.py` — Stage C: confirmatory re-solve,
  drift check, annotated wheel view, assembles `outputs/optimal/`
- `scripts/_sweep_common.py` — shared solver/geometry helpers used by
  Stages A and C
- `scripts/wheel_view.py` — the annotated side/front-view diagram
- `scripts/motion_study.py` — steer/roll/bump motion suite (8 motions) plus
  a solver-verified KPI/caster Newton solve, on top of a commanded KPI x
  caster grid (see below)
- `scripts/plot_motion_study.py` — diagnostic plots for `motion_study.py`'s
  output (currently: pure-steer 8-panel set, steer-at-fixed-roll overlay,
  bump-steer-family)
- `scripts/steering_rack_optimisation.py` — solves trackrod_inboard (rack X
  position) and trackrod_outboard (steering-arm pickup) from FVIC/SVIC
  alignment + the team's moment-arm target, sweeps rack X, scores bump/roll
  steer and Ackermann per candidate (see below)
- `scripts/plot_steering_rack_optimisation.py` — 6-panel candidate sweep
  figure plus best-candidate bump/roll/Ackermann/front-view detail plots for
  the script above
- `run_sweep.py` — earlier one-off sweep using the `kinematics` CLI directly
  (superseded, kept for reference only)
- `outputs/` — generated CSVs/plots, gitignored (not committed — run the
  scripts locally to regenerate):
  - `outputs/optimal/` — the current recommendation: final geometry, summary
    CSV, `RECOMMENDATION.md`, the annotated wheel view, and everything that
    applies to it (including `caster_and_trail/`, Stage B's own outputs)
  - `outputs/mount_height_kpi_sweep/` — Stage A's full grid search artifacts
  - `outputs/steering_rack_optimisation/` — rack-X sweep summary CSV plus
    `best_candidate/` (full bump/roll/steer sweep CSVs and geometry.yaml for
    the recommended candidate)
  - `outputs/_archive/` — outputs from the retired iteration1/2 scripts,
    kept for reference, not regenerated by anything current

## Current pipeline: merged mount-height / KPI / caster-trail optimisation

Three sequential stages replace what used to be three separate,
inconsistent sweep scripts (`iteration1_axle_sweep.py`,
`iteration2_upright_sweep.py`, `iteration2_kpi_sweep.py` — all retired).
Those three disagreed with each other on the tie-rod convention, KPI
rotation math, and solver invocation method; running one merged pipeline
instead of three separate "best of iteration N" results was the whole
point of this rewrite.

**Stage A** (`scripts/mount_kpi_sweep.py`) sweeps the upper wishbone
chassis-mount height (Z, 240mm up to the upright's height at KPI=0, 10mm
steps) against the kingpin inclination angle (KPI, 0–10°, 1° steps — a
front-view rigid-body rotation of the whole upright about the lower ball
joint). For every (Z, KPI) candidate it runs BUMP (±30mm) and ROLL (±25mm)
sweeps through the `kinematics` Python API and scores 7 of the team's 9
priority targets (bump steer, camber gain in roll, roll centre height, KPI,
scrub radius, roll steer, camber gain in bump — `caster_static` and
`mechanical_trail_static` are excluded here since a Z×KPI-only sweep can't
meaningfully move them). **The tie rod is *not* forced colinear** with the
rotated track-rod outboard — `trackrod_inboard` stays at its raw,
unmeasured CAD value throughout, per the correction already documented in
the old `iteration2_kpi_sweep.py`.

**Stage B** (`scripts/caster_trail_analysis.py`) is a purely geometric
(no solver) caster/mechanical-trail sweep applied on top of Stage A's
winning geometry: it rotates the kingpin axis through caster angles
0–7°, finds the rearward x-offset needed to land mechanical trail in the
10–20mm optimal band, and picks the candidate that maximises caster while
minimising that offset.

**Stage C** (`scripts/build_optimal_geometry.py`) combines both winners
into one geometry — note this moves **both** wishbones' outboard ball
joints from CAD, not just the upper one — re-solves it once to confirm
nothing drifted from Stage A's prediction, scores it against the full
9-target set, and renders the annotated wheel view (caster/KPI/camber/
scrub/trail labeled directly on a zoomed side + front view, unlike the
submodule's whole-assembly-scaled 4-view linkage render, where a few
degrees of tilt is invisible).

Known engineering choices baked into this pipeline (see git history / ask
if any of these should change):
- BUMP sweep travel is ±30mm (scripts 1/2's range), not the old script 3's
  −40/+120mm, which caused a 23% solver non-convergence rate in the last
  run before this merge — a 100+-candidate grid shouldn't carry that.
- Stage A drops the RACK sweep entirely (none of its scored/reported
  metrics need it) — only Stage C reproduces steering-travel behaviour, and
  only once, for the final geometry.

### Running it

```
python scripts/mount_kpi_sweep.py --plots
python scripts/caster_trail_analysis.py --geometry outputs/mount_height_kpi_sweep/best_zkpi_geometry.yaml --out-dir outputs/optimal/caster_and_trail
python scripts/build_optimal_geometry.py
```

Each stage also has a `--smoke` (or no-arg default, for Stage C) fast path
to sanity-check the wiring before running the full grid. See each script's
module docstring for the full CLI.

The latest recommendation is always in `outputs/optimal/RECOMMENDATION.md`
— not copied into this README, since that number goes stale the moment the
sweep re-runs (this bit us once already, see the 2026-08-05 changelog).

This is a purely geometric/kinematic-solver pipeline — it does not touch
CAD. Once hardpoints are actually moved, re-run all three stages against
the updated `configs/uct_front_geometry_generated.yaml` to re-validate.

### Motion study

`scripts/motion_study.py` runs load cases the 3-stage pipeline above never
exercises — steer/rack travel, combined roll+steer, single-wheel bump, and
a bump-steer gradient across several fixed steer angles — across a
commanded KPI x caster grid. KPI/caster are set via `apply_steering_axis` +
a Newton loop (`geometry_for_target_angles`) that corrects the commanded
ball-joint attitude until the *solver's own* `kpi_left`/`caster_left`
metrics hit the target, not just our own closed-form formula.

```
python scripts/motion_study.py --smoke                  # one variant, one motion
python scripts/motion_study.py --kpi 4 6 8 --caster 3 5 7   # full default grid
python scripts/plot_motion_study.py --kpi 6 --caster 5   # diagnostic plots for one variant
```

Outputs under `outputs/motion_study/`: `sweeps/` (reviewable motion YAMLs),
`runs/kpi{K}_caster{C}/` (one CSV per motion, every flat metric column plus
every solved point's `_x/_y/_z`), `index.csv` (target vs. achieved KPI/
caster per variant), `plots/`.

Currently a scoped first pass: only the pure-steer/steer-at-fixed-roll and
bump-steer-family plots are built (the ones diagnosing the bump-steer/
roll-steer failures found in Stage C). Deferred: the roll+steer cornering,
pure-heave, and pure-roll panel sets, cross-variant overlays, and a pytest
suite.

## Steering rack / tie-rod optimisation

`scripts/steering_rack_optimisation.py` solves the two unmeasured front
hardpoints — `trackrod_inboard` (rack X position) and `trackrod_outboard`
(steering-arm pickup on the upright) — from the wishbone-derived FVIC/SVIC
and the team's 150–200mm steering-moment-arm target, then sweeps rack X
from -250 to -100mm (ISO) scoring bump steer, roll steer and Ackermann on
each candidate. Read the module docstring before touching the constants —
it documents why the literal front-view+side-view IC intersection is not
used directly (it puts `trackrod_outboard` several **metres** from the
upright, because the SVIC sits ~26.7m away for this wishbone geometry) and
what buildable substitute is used instead.

Key finding: with this wishbone geometry, satisfying the front-view IC
(near-zero bump steer at static) pins `trackrod_outboard`'s Y so close to
the kingpin axis that no buildable steering-arm reach can also hit the
40–80% Ackermann target — even 500mm+ of arm only gets to the low end.
This is a genuine conflict between the moment-arm and Ackermann targets for
this car, not a search/tuning problem; see
`outputs/steering_rack_optimisation/run_log.txt` and the summary plot's
Ackermann panel. Rack X itself is chosen on bump/roll steer through travel,
which both improve monotonically toward the -100mm end of the search range
(candidates below about -200mm are kinematically infeasible for the
solved `trackrod_outboard` and are excluded, not silently skipped).

```
python scripts/steering_rack_optimisation.py --smoke   # 3 candidates, wiring check
python scripts/steering_rack_optimisation.py           # full 16-candidate sweep
python scripts/plot_steering_rack_optimisation.py       # summary + best-candidate plots
```

Outputs: `outputs/steering_rack_optimisation/summary.csv` (one row per rack
X candidate, `feasible=False` rows kept for the infeasible band),
`outputs/steering_rack_optimisation/best_candidate/` (full bump/roll/steer
sweep CSVs + resolved `geometry.yaml` for the recommendation), and five
PNGs under `outputs/` (`steering_rack_optimisation_summary.png` plus four
`best_candidate_*.png` detail plots).

## Changelog

### 2026-08-06 (motion study)
- Added `scripts/motion_study.py` and `scripts/plot_motion_study.py`,
  reviewed against a colleague's (Caitlin's) spec for a fuller motion
  suite — verified her 6 stated assumptions about the solver against
  source first (4 confirmed, 2 partially wrong: only one `ActuatorDOF` is
  actually validated, and `track_change` isn't a real solver column).
  Diagnosed the Stage C bump-steer failure isn't a "gets worse at full
  lock" problem — the `bump_steer_family` curves are roughly parallel, just
  offset by steer angle — so the fix is a general toe/travel slope issue
  (tie-rod length / rack height), not something specific to high steer
  angles. Also found roll measurably corrupts the steering geometry
  (~+1.2–1.3° added outside camber at fixed roll vs. pure steer).

### 2026-08-06
- Retired `iteration1_axle_sweep.py`, `iteration2_upright_sweep.py`, and
  `iteration2_kpi_sweep.py` — three separate sweeps that disagreed with
  each other (tie-rod convention, KPI rotation math, solver invocation,
  scoring polarity) and each produced its own separate "best" geometry.
  Replaced with one 3-stage pipeline (`scripts/mount_kpi_sweep.py` →
  `scripts/caster_trail_analysis.py` → `scripts/build_optimal_geometry.py`)
  that searches Z and KPI jointly, then refines caster/trail, then
  re-solves once to confirm nothing drifted.
- Adopted `iteration2_kpi_sweep.py`'s tie-rod convention (raw CAD
  `trackrod_inboard`, not forced colinear) as the one true rule going
  forward, and its 9-target weighted-cost scoring (trimmed to 7 for the
  Z×KPI grid, restored to all 9 for the final confirmatory solve).
- Switched the merged sweep to the ±30mm symmetric BUMP range (scripts
  1/2's convention) instead of script 3's −40/+120mm, which had caused
  36/154 solver non-convergence failures in the last run before this
  merge.
- Added `scripts/wheel_view.py`: a focused, zoomed side+front-view diagram
  with caster/KPI/camber/scrub radius/mechanical trail labeled directly on
  the drawing — the submodule's 4-view linkage renderer scales to the
  whole assembly's bounding box, making a few degrees of caster/KPI tilt
  over a ~150mm kingpin axis invisible.
- Reorganized `outputs/`: `optimal/` now holds everything for the current
  recommendation in one place (previously scattered flat in `outputs/`),
  `mount_height_kpi_sweep/` holds the grid-search artifacts, and
  everything from the retired scripts moved to `outputs/_archive/`.

- Constrained the sweep to physically valid mount positions: Y pinned to
  the lower wishbone's chassis plane, Z capped at the upright ball-joint
  height.
- Added `--render-best`: draws the actual linkage geometry at the
  top-scoring mount position.
- Outputs now default to `outputs/` instead of the repo root.
- Fixed the solver's geometry-plot legend (was covering the drawing;
  listed every mirrored left/right part twice) — submodule change,
  `suspension-model@6f6a72d`.
- Replaced every hand-typed fixed hardpoint (lower wishbone, upper ball
  joint, track rod, axle, CG, tire, wheelbase) with values loaded straight
  from `configs/uct_front_geometry_generated.yaml`. The hand-typed lower
  wishbone had the chassis-side mount ~35mm *above* the upright mount; the
  real CAD has it ~10mm *below* — an inverted relationship that was
  inflating the computed roll centre height. Fixing it dropped roll centre
  height at the sweep's best point from over 100mm to 44mm, inside the
  20–50mm target band, and raised the best total score from 0.488 to 0.770.
- Discovered the real chassis puts the upper wishbone's front/rear legs at
  different Y (not one shared mounting plate) — each leg is now pinned to
  its own lower-wishbone counterpart's Y instead of a single shared value.
- Forced the tie rod level and colinear with the rack (both pinned to the
  outboard mount's X and Z) — the CAD's rack-side point was an unmeasured
  placeholder, and a kinked or raked tie rod doesn't steer cleanly. Raised
  the best total score to 0.810.
